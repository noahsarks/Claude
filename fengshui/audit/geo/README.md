# 商业风水软件的「地理位置」逻辑：反编译与横向对比

日期：2026-09-02。范围：只看地理位置，不看户型图。

---

## 〇、先说 APK 反编译的结果：没拿到包，但拿到了等价物

**尝试过的路径与失败点**（都可复核）：

| 路径 | 结果 |
|---|---|
| apkcombo.com 搜索 → POST `/{slug}/{pkg}/{xid}/dl` | ✅ 拿到变体列表与 base64 下载链 |
| 解码后的 `download.pureapk.com/b/APK/…` | ❌ 302 跳 `apkpure.com/url?…`，Cloudflare 对机房 IP 返回 403 |
| apkpure / apkfab / apk.support / androidappsapk / androidfreeware | ❌ 全部 403（同一层反爬） |
| apkmonk | ❌ 网关 502（出口策略拒绝） |
| 无头 Chromium（本机已装，走会话代理） | ❌ 所有站点 `ERR_CONNECTION_RESET`——该 Chromium 未加载代理 CA。按环境规则不得关闭 TLS 校验，故此路封死 |
| 小米应用商店 / 应用宝 / 华为应用市场 搜「风水」 | ❌ 返回的全是游戏与工具，**风水类应用在大陆商店已被清理** |
| 华军软件园 / 非凡 / 绿色下载站 搜「风水」 | ❌ 同上，返回 360 安全卫士、WPS、抖音之类的默认热门 |

**这本身是一条发现**：风水类软件在大陆分发渠道基本不存在，
它们活在 Google Play 的港台/海外市场，而 Google Play 的镜像站对机房 IP 一律反爬。

jadx 1.5.1 已装在 `/home/user/rev/jadx`，一旦有 APK 即可直接跑。

**替代物**：`fscalc.com` 是一个真实运营的商业风水计算站（付费墙 + Stripe），
整个应用是一个 **734 KB 的生产环境压缩 JS 包**——与 APK 同性质的编译产物，
且**完全可读**。摘录存于 `fscalc_extract.js`。
它的宣传语是 "upload your own floorplan and use the **Google Maps based Virtual Compass**"，
即明确以经纬度为输入。这正是要找的「用地理位置的商业软件」。

## 一、商业软件的地理逻辑：只有磁偏角，没有别的

fscalc 反编译后，**唯一**接触经纬度的代码路径是：

```javascript
var e = { lat1: this.get("latLng").lat(), lon1: this.get("latLng").lng(), resultFormat:"xml" },
    i = "/api/getNoaa?" + $.param(e);
…
parseSuccess: function(t){
    var e = parseFloat(t.declination).toFixed(1);   // ← 四舍五入到 0.1°
    this.addToNoaaCache(…);
    this.set("magneticNorthOffset", e);
}
```

即：**经纬度 → NOAA `calculateDeclination` → 磁偏角 → 旋转罗盘叠加层。完。**

其余与地理有关的字段只有 `mapImage / latLng / zoom / rotatedImage`——
Google Maps 卫星图当作可旋转的背景底图。全包搜索：

```
elevation 0   terrain 0   slope 0   river 0   road 0
altitude  0   landform 0  contour 0  DEM 0
```

**没有任何地形计算。** 与之前读 suangua / Horosa 的结论完全一致：
「地理位置」在商业风水软件里 = 磁偏角查询，仅此而已。

## 二、同一位置，三个引擎算出什么

链条：**罗盘读数 --(磁偏角)--> 真方位角 --(24 山界)--> 坐山 --(挨星)--> 格局**
三段各有分歧点。九运（2024–2043）。

三个引擎的地理步骤：

| 引擎 | 磁偏角来源 | 时点 | 符号约定 | 粒度 |
|---|---|---|---|---|
| fscalc（商业） | NOAA WMM 在线 API | 实时（现为 WMM-2025） | 东偏为正 | 连续，按经纬度 |
| Horosa（开源） | 内置城市查表 | **2013-06 快照** | **西偏为正** | ~340 个城市，不插值 |
| suangua（开源） | 无 | — | — | 度数照单全收 |

### 磁偏角本身的分歧（NOAA 2026-09 实测）

| 城市 | NOAA(东正) | 换算西偏 | Horosa 2013 表 | 差 | 占 15° 山 |
|---|---|---|---|---|---|
| 洛阳 | −5.24 | 5.24 | 4.42 | +0.82 | 5.5% |
| 杭州 | −6.09 | 6.09 | 5.08 | +1.01 | 6.7% |
| 北京 | −7.56 | 7.56 | 6.58 | +0.98 | 6.5% |
| 哈尔滨 | −11.36 | 11.36 | 10.47 | +0.89 | 6.0% |
| 广州 | −3.28 | 3.28 | 2.57 | +0.71 | 4.8% |
| 乌鲁木齐 | +2.50 | −2.50 | −2.68 | +0.18 | 1.2% |
| 拉萨 | −0.07 | 0.07 | −0.12 | +0.19 | 1.3% |
| 西安 | −4.19 | 4.19 | 3.48 | +0.71 | 4.7% |

13 年的长期变化把中国东部的磁偏角推走了约 **0.7–1.0°**。

### 端到端：同一罗盘读数，三种结论

```
── 杭州  罗盘读 178.0° ──
   fscalc   真方位 171.91°  坐壬  → 双星到向
   horosa   真方位 172.92°  坐子  → 双星到坐
   suangua  真方位 178.00°  坐子  → 旺山旺向
   坐山不一致（壬/子）；格局三者互不相同

── 洛阳  罗盘读 172.0° ──
   fscalc   166.76°  坐壬  → 双星到向
   horosa   167.58°  坐壬  → 双星到向
   suangua  172.00°  坐壬  → 上山下水     ← 坐山一致，结论仍相反

── 哈尔滨 罗盘读 186.0° ──
   fscalc   174.64°  坐子  → 双星到坐
   horosa   175.53°  坐子  → 双星到坐
   suangua  186.00°  坐子  → 旺山旺向
```

## 三、差异归因

扫过全部罗盘读数（0–360°，0.1° 步长，3600 个），把分歧拆成两个来源：

| 城市 | 坐山分歧 | fscalc-Horosa | fscalc-suangua | 格局分歧 | **仅挨星致** |
|---|---|---|---|---|---|
| 洛阳 | 35.3% | 5.3% | 35.3% | 100% | 64.7% |
| 杭州 | 40.7% | 6.7% | 40.7% | 100% | 59.3% |
| 北京 | 50.7% | 6.7% | 50.7% | 100% | 49.3% |
| 哈尔滨 | 76.0% | 6.0% | 76.0% | 100% | 24.0% |
| 广州 | 22.0% | 4.7% | 22.0% | 100% | 78.0% |
| 乌鲁木齐 | 17.3% | 1.3% | 16.0% | 100% | 82.7% |
| 拉萨 | 1.3% | 1.3% | 0.7% | 100% | 98.7% |
| 西安 | 28.0% | 4.7% | 28.0% | 100% | 72.0% |

实测与理论值 `|Δ磁偏角| / 15°` 逐城吻合（如杭州 40.7% vs 40.6%）。

**三个成因，按量级排序：**

**① 不做磁偏角校正（最大）。** 山宽 15°，中国东部磁偏角 3–11°，
所以「直接把罗盘读数当真方位角」在哈尔滨会让 **76%** 的读数落到错误的山上，
北京 51%，杭州 41%，广州 22%。只有拉萨（磁偏角 ≈0）无所谓。
suangua 完全不处理磁偏角——它把度数当成用户已经校正过的真方位角，
但界面上没有任何地方说明这一点。

**② 磁偏角数据陈旧（中等，但会随时间线性增长）。**
Horosa 的表是 2013-06 快照且明确拒绝外推。13 年过去，
中国东部已偏 0.7–1.0°，即 **4.7–6.7% 的读数会落到相邻的山**。
年变率约 −0.02 至 −0.04 °/年，所以到 2040 年这个数字会翻倍。

**③ 挨星规则算错（不随地理变化，但在九运是全错）。**
suangua 误用「坐山自身阴阳」而非「入中之星所属卦中同元龙之山的阴阳」。
216 局中错 156 局；**九运 24 山全错（24/24）**——
即 2024–2043 年间，它对任何一栋房子的格局判断都是错的。
所以上表「格局分歧 100%」不是巧合。

**④ 一个尚未发生但一碰就大的坑：符号约定。**
Horosa 的表以西偏为正，WMM/IGRF 以东偏为正。该文件自己在头部警告了这一点。
若有人换数据源时忘了取负：

| 城市 | 符号错导致的偏差 | 相当于 |
|---|---|---|
| 哈尔滨 | 22.73° | 1.52 个山 |
| 北京 | 15.11° | 1.01 个山 |
| 杭州 | 12.17° | 0.81 个山 |
| 洛阳 | 10.48° | 0.70 个山 |

误差是磁偏角的两倍，在北方直接跨过整整一个山。

## 四、顺带确认：谁的挨星是对的

三方独立实现 × 9 运 × 24 坐山 = 216 局：

```
沈氏标准（本项目参考实现）  基准
fscalc（商业，奇偶式写法）  216/216 一致
Horosa（开源，元龙查表式）  216/216 一致
suangua（开源）             60/216 一致（27.8%）
```

fscalc 的写法很紧凑，值得记下——它不查表，直接用入中之星的**奇偶**：

```javascript
oddStarDirections  = ["yang","yin","yin"];   // 入中星为奇数卦(1,3,7,9)：地元阳、天元阴、人元阴
evenStarDirections = ["yin","yang","yang"];  // 偶数卦(2,4,6,8)：反之
…
var g = p; if (5 == p) g = u.originalLoShu;  // 五入中 → 取该宫本身的洛书数定奇偶
var m = this.evenStarDirections[d];
this.isOdd(g) && (m = this.oddStarDirections[d]);
```

这与「入中之星所属卦中同元龙之山的阴阳」严格等价（含五入中的情形，实测 0/216 分歧）。

参考实现另外复现了三条公认的结构性质，作为自检：
一运与九运各 12 双星到向 + 12 双星到坐（**无旺山旺向、无上山下水**）；
五运 12 旺山旺向 + 12 上山下水；二三四六七八运各 6/6/6/6。

## 五、对本项目的意义

1. **「地理位置风水」在商业软件里是空白，且空白得比想象中彻底。**
   最像地理产品的 fscalc，其全部地理计算就是一次 NOAA 磁偏角查询；
   Google 卫星图只是个可旋转的背景。没有任何软件对位置本身评分。

2. **但同一个空白里已经有一个真实的、可量化的、没人做对的问题：坐向定位。**
   磁偏角不做、做错、或用过期数据，能让 20–76% 的案例落到错误的山上，
   而山错则整盘全错。这是一个有明确对错、可验证、当前普遍做错的功能——
   与我们那个信噪比 1:1、无法验证对错的地形评分完全相反。

3. **若要做地理方向，最稳的第一块砖是「坐向定位」而不是「地形评分」：**
   输入经纬度 + 日期 → WMM/IGRF 实时磁偏角（带符号约定与年代说明）
   → 真方位角 → 24 山（标注离边界多远、是否兼向）→ 正确挨星起盘。
   每一步都有唯一正确答案，可用 216 局表做回归。

## 六、复现

```bash
python3 decl.py        # 拉 NOAA WMM 实测值，与 Horosa 2013 表对照
python3 pipeline.py    # 同一罗盘读数 → 三引擎的真方位角/坐山/格局
python3 attribute.py   # 扫 3600 个读数，把分歧拆成地理成因与挨星成因
```

`pipeline.py` 自带三种挨星规则（`std` / `fscalc` / `suangua`），
其中 `fscalc` 一支是从生产 JS 包逐行移植的。
