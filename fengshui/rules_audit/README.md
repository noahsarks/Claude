# 规则逐条核对 —— 对着原始文本

**为什么现在才做**：当初抽规则用的是二手来源（`youngzs/xuanxue` 仓库的 `docs/`）。
现在《欽定古今圖書集成·堪輿部》30 卷已入库（`../masters/corpus/gjtsjc/`），
其中卷 670 就是**缪希雍《葬经翼》全文**——16 条规则里有 9 条出自它。
第一次可以拿原文逐字核。

核对方法：把每条规则的 `quote`、`metric` 与卷 670 原文并置，看三件事——
① 引文是否属实 ② 实现是否忠于引文 ③ 原文有而规则没有的，是不是可算却漏了。

## 一、龙虎（R2）：`balance` 项没有文本依据

### 原文（卷 670 四獸砂水篇）

> 貼身左右二砂，名之曰「龍虎」者，以其護衛區穴，不使風吹，**環抱有情，
> 不逼不壓，不折不竄**，故云：「**青龍蜿蜒，白虎馴頫**。」反是者為銜尸，為嫉主。

### 现行实现

```python
near_hu = .40*pl(min(L_rise, R_rise), …)                      # 有砂
        + .35*(1 - abs(L_rise-R_rise)/max(|L_rise|,|R_rise|,1))  # ← balance
        + .25*pl(max(L_ang, R_ang), …)                        # 不逼不压
```

### 问题

原文对龙虎的要求是四条：**环抱有情、不逼、不压、不折、不窜**。
**没有一条要求左右对称。**

而且「青龍**蜿蜒**，白虎**馴頫**」是给左右两侧规定了**不同**的形态——
龙要蜿蜒（蜿曲延伸），虎要驯頫（俯首驯服）。若原文期待对称，
不会给两侧起不同的名目、提不同的要求。

`balance` 在 `hulong` 里占 0.35，而 `near_hu` 又占 `hulong` 的 0.70，
即**这一项占该分量的 24.5%**，而 `hulong` 在山地模式下权重 0.11、平原 0.06。

### 处理

- 短期：`balance` 标为 `source: 无`，与其余各项分开报告，不计入总分
- 需要补的是原文真正要求的两项：**不折**（左右砂中段是否凹折断开，
  已有 `F3_折臂` 但只作凶格，未作龙虎的组成条件）与**不窜**（砂尾是否外撇不回头）

## 二、明堂（R4）：原文定义是水，实现里一滴水都没有

### 原文（卷 670 明堂篇）

> 「明堂」者，**穴前水聚處也**……
> 其二龍虎內二水合處，名「**中明堂**」……
> 其三乃外洋大勢……通名之曰「**外洋大明堂**」。
> 大抵《明堂》以**聚水為上，橫抱次之，朝水又次之**，
> 交互有情、不見水去而順流者又次之。

原文给了两件事：**明堂是水聚之处**，且**水的形态有明确四级序**
（聚水 > 横抱 > 朝水 > 顺流）。

### 现行实现

```python
inner = .30*pl(front_slope) + .25*pl(front_drop) + .45*pl(front_open)
outer = .55*pl(outer_open)  + .45*(.6*pl(an_ang) + .4*pl(chao_ang))
mingtang = .60*inner + .40*outer
```

**六个分项全是地形：坡度、落差、开阔度、案山仰角、朝山仰角。没有一项是水。**

### 问题

`mingtang` 权重 0.18（山地）/ 0.22（平原），是第二或第三大分量，
而它测的东西与原文对明堂的定义不是同一件事。

引擎里确有 `water` 分量（0.24/0.34），含 `bank`（凹凸岸，近似「横抱」）
与 `sinuosity`。但：

- **「聚水」（穴前水的汇聚/滞蓄）没有任何对应量**
- **四级序（聚>横抱>朝>顺流）完全没有实现**
- 水与明堂被拆成两个独立分量相加，而原文里它们是同一件事的两面

### 值得记的一点：两层明堂的出处应改

`rules_luantou.yaml` 的 `new_metrics.M_明堂两层` 标的出处是
「清代遵化九凤朝阳峪万年吉地相度记载」。
**但两层（中明堂 / 外洋大明堂）的划分就在《葬经翼·明堂篇》里，早四百年。**
清代档案是旁证，不是出处。

### 处理

- `mingtang` 增设水项：穴前扇区内的**汇流累积量**与**水面/低洼面积占比**作为「聚水」的代理
- 「横抱」用现有 `bank`（凹岸）；「朝水」用是否有水自前方流来；「顺流」为水径直流走
- 四者按原文序做**有序**赋值，而非并列加权

## 三、F7 只是取名不当（初稿在此判错，已更正）

F7 的 `quote` 是：

> 虎蹲者，形反而凶僭且逼也；龙踞者，势凌而压强且窜也

对照卷 670 原文：

> 虎蹲者，形反而兇，僭且偪也。龍踞者，勢凌而壓，強且竄也。

**逐字属实。** F7 实际上把《穴病篇》十五条里的**虎蹲**与**龍踞**两条合并实现了，
出处标注 `葬经翼/003穴病.md` 也是对的。

唯一的问题是 **id 取名 `F7_gaoya`（高压）**——「高压」不是穴病名。
卷 670 中「壓」字出现在三处，都不是独立穴病：
「四山高而不壓」（下聚穴形的合格条件）、
「環抱有情，不逼不壓」（龙虎要求，属 R2）、
「龍踞者，勢凌而壓」（即 F7 本身）。

**处理**：改名为 `F7_hudun_longju`（虎蹲龙踞）。

**这处判错值得记**：初稿只按 id 名去原文里搜「高压」，没搜 `quote`。
id 是我起的，`quote` 才是证据——**核对必须以 quote 为准，不能以 id 为准**。

**十五条里实现了七条**（拒尸、墜足、折臂、割腳、破面、虎蹲、龍踞），
**两条可算而未实现：貫頂、朱雀騰去**。

- **貫頂**（脉连脑抽，星峰不现）：背后无独立局部高点即犯。可用 R1 已有的
  `backing` 与背后局部极大值检测直接判，几乎零成本。
- **朱雀騰去**（水倾反而朝斜背）：与 `F5_反跳` 相关但不同——
  反跳只论水的凹凸岸，騰去还要求「朝斜背」（前砂背向穴）。
  应与 R3 的 `facing_ratio` 联用。

注意虎蹲与龍踞（F7）正是原文对左右砂的两个凶格，与第一节 R2 的
「不逼不压」呼应——**它们已经在了**，所以第一节说 `balance` 该被替换掉的东西，
其实已有一半落实。

## 五、无法核对的两条：语料里没有《雪心賦》

`R7_shuikou_guansuo` 与 `F5_fantiao` 都标 `source: 雪心赋/003论水法.md`。

机械核对给出 0.36 / 0.40 / 0.82，但**这不构成否证**——
入库的《古今图书集成·堪舆部》30 卷里**没有《雪心賦》全文**
（卷 666/669/673/679 只是提到书名或转引片段；卷 679 名流列传记
「濮都監名應天，字則巍……作《雪心賦》」）。

语料里确有全文的是：青囊海角經、青烏先生葬經、管氏地理指蒙、
楊筠松十二杖法、**黃妙應博山篇（卷 666）**、繆希雍葬經翼（卷 670）、
水龍經、陽宅十書。

所以 R4/R5/R6/R9 标注「博山篇」并定位到卷 666、匹配 1.00，是**真核对通过**；
而 R7/F5 是**待补语料**，不是引文有问题。

## 七、核对方法本身也要标定

`quote_check.py` 用「最长公共子序列 / 引文长度」比对。**这个指标有噪声底。**

阴性对照：拿四句伪造的、风格相似但原文绝无的句子去比——

| 伪造句 | LCS 比 |
|---|---|
| 穴前三山并起，其气必聚，主子孙昌盛 | 0.47 |
| 水从西北来者，其局必贵，不可轻泄 | 0.43 |
| 左有金鸡右有玉犬，中藏紫气，法当大发 | 0.38 |
| 龙自东南入首，砂水俱备，斯为上吉之地 | 0.38 |

**噪声底约 0.38–0.47。** 35 万字的语料里，任何常用字组合都能凑出子序列。

于是判读标准应为：

| 分数 | 判读 |
|---|---|
| ≥0.85 **且能定位到具体卷** | 属实 |
| ≥0.85 但只定位到「部分」 | 多半是简繁/异体导致精确子串失配，需人工确认 |
| 0.5–0.85 | **不足为凭** |
| <0.5 | 与伪造句同级 |

按此重判，F1（0.82）与 F5（0.82）原本被我记为「部分吻合」，
其实**不足为凭**——但人工核对 F1 的引文「元武拒尸者，星峰无降势也」
与原文「「元武拒尸」者，星峰無降勢也」逐字一致，是真的。
说明该指标对**短引文**（十余字）两个方向都不可靠：既会虚高，也会虚低（窗口切分所致）。

**结论：机械核对只能用来筛，不能用来判。筛出可疑项后必须人工回原文看。**

## 八、这次核对说明了什么

修正后的账：

| 类别 | 条目 |
|---|---|
| **我加的、原文没有的** | `balance`（左右对称） |
| **原文有而漏实现的** | 明堂的水（含四级序）、貫頂、朱雀騰去、R7 的对象条件 |
| 命名不当 | `F7_gaoya` → 应为 `F7_hudun_longju` |
| 无法核对 | R7、F5（《雪心賦》不在语料） |
| **我在审计里判错又改回的** | F7 的出处与实现状态 |

第一类最危险：漏实现只是不完整，**凭空添加的项会主动制造信号**。
`balance` 占 `hulong` 的 24.5%，而 `hulong` 参与全部验证——
此前所有增益数字里都掺着这一项。

**教训一**：从二手整理稿抽规则，与从原文抽规则，不是同一件事。
在拿到原文之前，`rules_luantou.yaml` 里每条 `source` 字段给人的
「可回溯」印象是虚的——能回溯到的只是别人的整理稿。

**教训二**：核对要以 `quote` 为准，不能以 `id` 为准。
id 是我起的名字，`quote` 才是证据。初稿判错 F7 就是因为按 id 名去搜原文。
